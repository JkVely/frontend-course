S5 — TypeScript: tipos que hablan antes de que rompa

Abre la Consola en glud.org y escribe: const edad = "veintiuno"; console.log(edad + 5). En JavaScript el resultado es "veintiun005". ¿Te gustaría que el navegador te avise *antes* de ejecutar que estás sumando texto con número? TypeScript es el guardián que lo hace.

PREGUNTA GUÍA: mostrar el poder de TypeScript para detectar errores antes de la ejecución. Pedir a un voluntario que ejecute el ejemplo en la consola y observe el resultado inesperado. Luego explicar que TypeScript añade una capa de verificación estática que captura esos errores en tiempo de compilación, evitando que lleguen al usuario. Esto establece el tono de la sesión: trabajar con contratos que nos avisan temprano.

Objetivos de la sesión

Al terminar vas a poder:

  1. Explicar por qué JavaScript es dinámicamente tipado y qué costo tiene.
  2. Instalar y configurar TypeScript en un proyecto Astro/HTML.

  4. Usar interfaces para describir formas de datos.
  5. Comprender union types, literal types y null/undefined.
  6. Leer errores de compilación y usarlos para corregir código antes de ejecutar.
  7. Conectar lo aprendido con el caso real: cómo TypeScript protege los datos del formulario de SLUD y la lógica de eventos.

TypeScript es JavaScript, pero con contratos. No cambia cómo corre el navegador, cambia cuándo te enteras de los errores.

Recorrer cada objetivo, conectando con los bloques de contenido que siguen. Resaltar que la tipificación estática cambia el flujo de trabajo: escribimos, compilamos, corregimos y luego ejecutamos. Enfatizar la ventaja de detectar errores en el editor antes de que el usuario los vea en la página.

El problema: JavaScript no avisa hasta que corre

Tipado dinámico y su costo

let edad = 21
edad = "veintiuno"   // válido en JS
console.log(edad + 5) // → "veintiuno5"

En JS los tipos se deciden en tiempo de ejecución. Eso permite rapidez, pero también errores silenciosos.

El error aparece cuando el usuario usa la página. TypeScript mueve la verificación a tiempo de compilación: antes de subir nada, el compilador revisa contratos.

Paralelo Minecraft: JS es como construir con redstone a prueba y error; TS es como tener el circuito dibujado en papel, revisado, y luego montarlo. Si el papel está mal, no llega a la partida.
Explicar que el tipado dinámico permite flexibilidad pero a costa de seguridad. Mostrar ejemplos comunes de errores que solo aparecen en runtime (sumar string y número, acceder a propiedad inexistente, etc.). Destacar que TypeScript no elimina JavaScript, sino que agrega una capa de revisión estática. Usar la analogía de Minecraft para ilustrar la diferencia entre improvisar y planificar con antelación.

Instalar y configurar TypeScript

Preparando el proyecto

En un proyecto Astro/HTML:

corepack pnpm add -D typescript
npx tsc --init

tsconfig.json mínimo:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  }
}

Esto hace que el compilador sea estricto: no permite any implícito, exige inicialización, etc.

Guiar a los estudiantes a ejecutar los comandos en sus proyectos. Explicar cada opción del tsconfig: target y module para compatibilidad, strict para activar todas las reglas de seguridad, esModuleInterop para mejor compatibilidad con CommonJS, skipLibCheck para acelerar compilación. Enfatizar que iniciar con configuración estricta es una buena práctica que se puede relajar posteriormente si es necesario.

Declarar con tipos

Tipos básicos

let nombre: string = "Mónica"
let edad: number = 21
const activo: boolean = true

let tags: string[] = ["frontend", "astro"]
let colores: Array = ["rojo", "verde"]

let usuario: { nombre: string; edad: number } = {
  nombre: "Andrés",
  edad: 19
}

Si cambias el tipo, el compilador te avisa:

nombre = 123  // Error: Type 'number' is not assignable to type 'string'
Explicar cada tipo básico y sus usos típicos. Mostrar cómo la sintaxis : tipo se agrega después del nombre de la variable. Destacar la diferencia entre let y const. Mostrar el error en tiempo de compilación cuando se intenta asignar un valor de tipo incorrecto. Animar a los estudiantes a probar estos ejemplos en sus propios archivos .ts y observar los mensajes de error.

Interfaces: la forma de los datos

Definiendo contratos de objetos

interface Estudiante {
  nombre: string
  edad: number
  cursos?: string[]   // opcional
  activo: boolean
}

const estudiante: Estudiante = {
  nombre: "Daniela",
  edad: 20,
  activo: true
  // cursos es opcional
}

Ventaja: si alguien cambia la propiedad nombre a name, TypeScript lo señala en todos los usos.

Explicar que las interfaces describen la forma que deben tener ciertos objetos, actuando como contratos. Destacar la sintaxis para propiedades opcionales (?) y cómo el compilador las trata. Mostrar cómo cambiar un nombre de propiedad genera errores en todos los lugares donde se usa la interfaz, lo que facilita el refactor seguro. Animar a los estudiantes a pensar en interfaces como documentación viviente que el compilador hace cumplir.

Union types y literal types

Tipos que aceptan varios valores

type Rol = "estudiante" | "profesor" | "admin"

function saludar(rol: Rol) {
  console.log(`Hola ${rol}`)
}

saludar("estudiante") // ok
saludar("invitado")   // Error

Literal types protegen el flujo: una variable no puede ser solo "cualquier string", puede ser exactamente "activo" | "inactivo".

Explicar cómo los union types permiten que una variable tenga uno de varios tipos específicos. Mostrar cómo los literal types (tipos basados en valores concretos) otorgan un control preciso sobre los valores permitidos. Destacar la ventaja de detectar en tiempo de compilación cuando se pasa un valor no esperado (como "invitado" en el ejemplo). Animar a los estudiantes a pensar en union types para modelar estados, roles, o cualquier conjunto finito de valores válidos.

null, undefined y strict null checks

Manejo seguro de valores ausentes

let valor: string | null = null
valor = "hola"

// valor.length funciona porque el compilador sabe que no es null ahora

Con strict: true, TypeScript distingue null/undefined.

Patrón seguro:

if (valor !== null) {
  console.log(valor.length)
}
Explicar cómo en modo strict, null y undefined son tipos distintos y deben ser considerados explícitamente. Mostrar cómo los tipos de unión (string | null) obligan a comprobar el valor antes de usarlo. Destajar el patrón de guarda (if (valor !== null)) y cómo TypeScript reduce el tipo dentro del bloque. Animar a los estudiantes a practicar este patrón para evitar errores comunes como "Cannot read property 'length' of null".

Caso real glud.org con tipos

Aplicando TypeScript al proyecto

Imagina que el botón de copiar correo recibe datos de un objeto:

interface BotonCopiar {
  email: string
  textoVisor: string
}

function copiar(boton: BotonCopiar) {
  // lógica de copiar al portapapeles
}

Si alguien pasa { mail: "..." } en lugar de email, TypeScript lo detecta antes de desplegar. En JS ese error aparece cuando el usuario hace clic y el botón no hace nada.

En el formulario de inscripción SLUD:

interface Inscripcion {
  nombre: string
  correo: string
  cursoId: number
}

Con tipos, no puedes enviar un número donde va un correo. Eso evita correos inválidos en la base de datos.

Conectar los conceptos aprendidos con el sitio real del GLUD. Mostrar cómo definir interfaces para los objetos que el sitio maneja (como datos de formularios o configuraciones) ayuda a prevenir errores de integración. Destacar que TypeScript no cambia el comportamiento en tiempo de ejecución, pero sí asegura que los datos que pasamos a funciones tengan la forma esperada. Animar a los estudiantes a pensar en cómo aplicar estas ideas en sus propios proyectos del grupo.
