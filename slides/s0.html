Las piezas de una página

Toda página web son 3 capas

CapaTecnologíaSiglaQué hace
EstructuraHTMLHyperText Markup LanguageEl contenido y su significado (qué es cada cosa)
PresentaciónCSSCascading Style SheetsCómo se ve: colores, tamaños, posiciones
ComportamientoJSJavaScriptQué pasa cuando interactúas con la página
Minecraft: HTML son los bloques colocados (qué es la casa). CSS son los materiales y acabados (cómo luce). JS es la redstone (cómo reacciona la casa a ti).
Expandir SIGLAS una por una: - HTML = HyperText Markup Language. "Markup" quiere decir que la página es texto con marcas (etiquetas) que le dicen al navegador qué significa cada cosa: un título, un párrafo, un enlace. "HyperText" = texto que enlaza a otro texto (los links). - CSS = Cascading Style Sheets. "Cascading" (en cascada) se refiere a cómo se resuelven las reglas cuando varias se contradicen: gana la más específica o la que viene después. "Style Sheets" = hojas de estilo: reglas que le dicen al navegador cómo pintar. - JS = JavaScript. NO tiene relación con Java (confusión histórica famosa: se llamó así por marketing en los 90). Es el único de los tres que programa: lógica, condiciones, repeticiones. Dato importante: el navegador es quien ejecuta Y pinta las tres capas juntas. "Ver la página" = el navegador tomó el HTML, aplicó el CSS y ejecutó el JS.

La capa estructura

HTML: hoy en el navegador, abrimos la caja

<header>
  <nav> ... enlaces ... </nav>
</header>
<main>
  <h1>Grupo GNU/Linux de la Distrital</h1>
  <p>Promovemos el software libre...</p>
</main>

Las etiquetas no solo «envuelven» texto: definen su significado. Ese significado es lo que usan el navegador, los buscadores y los lectores de pantalla.

Acción EN VIVO (pedazo clave de la clase): abrir glud.org, clic derecho, "Ver código fuente" / "Inspeccionar". Señalar que lo que ven es texto plano con etiquetas. Enseñar a leer 3 etiquetas de verdad: <h1> (encabezado principal, solo uno por página), <p> (párrafo), <a> (enlace animado el cursor). Y <header>,<main>,<footer> = regiones estructurales. Mensaje base: HTML NO es "código para decorar". Es "código para significar". Esta distinción es la puerta de entrada a la accesibilidad del curso: si la etiqueta dice qué significa, una persona ciega con lector de pantalla recibe la misma información que alguien viendo. En S2 y S11 esto vuelve.

La capa presentación

CSS: las reglas para pintar

Cada regla tiene un selector (a quién le aplico) y unas propiedades (qué le digo que sea).

h1 {
  color: cyan;
  font-size: 3rem;
  text-shadow: 0 0 20px cyan;
}
.btn {
  background: cyan;
  border-radius: 8px;
  padding: 12px 24px;
}

Mismo HTML, dos CSS distintos: el contenido es igual, la experiencia cambia. Hacemos la prueba en vivo con un archivo.

Comida: CSS es el emplatado y la presentación del plato. Los ingredientes (HTML) son los mismos; el emplatado decide si al comensal le dan ganas de comer o no.
Demo con los 2 archivos del repo: material/ejemplos/hero-malo.html y hero-bueno.html. Abrirlos uno al lado del otro. Mostrar que el CONTENIDO es casi idéntico (misma información, misma marca) pero el CSS cambia todo: contraste, jerarquía, espaciado, legibilidad. Leer juntos una regla del hero-bueno (ej: .btn-primary) y una del hero-malo (ej: h1 o la fuente Comic Sans) para que sin saber CSS ya sepan LEERLO: "esto le dice a tal elemento que sea así". Aviso: esto es el adelanto de S2 (diseño) y S9 (Tailwind). Hoy solo queremos que entiendan el mecanismo selector + propiedades.

La capa comportamiento

JavaScript: la única capa que programa

  • Se escribe dentro de <script> o en archivos .js.
  • Lo ejecuta el navegador del visitante, en su propia máquina.
  • Manipula las otras dos capas: cambia textos, estilos, apariencia de elementos.

Ejemplo real en glud.org: el botón "copiar correo" y el panel móvil que se desliza corren por JavaScript. El resto de la home... no usa JS.

Concepto clave para sembrar hoy y cosechar en S10: el JS corre del lado del CLIENTE (la máquina del visitante), NO en el servidor. Eso tiene costo: el visitante debe descargar y ejecutar ese código; por eso "poco JS" = "página más rápida de cargar". Dato medible de glud.org: su página principal solo carga ~8 KB de JS propio. Para contexto: una foto típica de WhatsApp pesa más. La decisión "usar poco JS" es deliberada y la retomamos en S7 (Astro justamente existe para eso). Si alguien pregunta "¿entonces con qué se hace la página dinámica si no hay JS?" — no: ahí está el matiz. Hay JS en el navegador (que vimos) y hay programas en el servidor que GENERAN el HTML (SSR/SSG, lo vemos en esta misma sesión, slides 10-13). Cosas distintas.

El viaje empieza

Antes del viaje: las siglas de la carretera

SiglaSignificadoPapel en el viajeAnalogía
URLUniform Resource LocatorLa dirección completa que escribesLa dirección postal completa
DNSDomain Name SystemTraduce el nombre a un númeroLa guía telefónica / el portero
IPInternet ProtocolEl número identificador de cada máquinaLas coordenadas de cada casa
HTTP(S)HyperText Transfer Protocol (Seguro)El idioma del pedido entre máquinasEl protocolo de la petición
Ir despacio aquí: estas 4 siglas confunden a todo el mundo y explican el 90% de los "no me carga el sitio" que verás en la vida. - URL es lo que TÚ escribes: https://glud.org/. Tiene partes: protocolo (https://), dominio (glud.org). No hace falta más por hoy. - DNS: los humanos recordamos nombres, las máquinas números. El DNS es ese directorio gigante y distribuido que dice "glud.org = 75.2.96.93". Metáfora fuerte: en la ciudad real no dices "vive en lat 4.65, lon -74.03", dices "Calle 40 con Cra 7"; DNS hace esa traducción por ti. - IP: el número único que identifica una máquina en la red. V4 (cuatros grupos: 192.168.x.x) vs V6 (hexadecimal, más largo) — mencionar de pasada que IPv6 existe porque los números V4 se agotaron. - HTTP: el "idioma" del pedido. GET = "dame eso". HTTPS = el mismo idioma pero por un canal cifrado (la "S" de Secure). Regla práctica: HTTPS es obligatorio hoy, no opcional. Mini-ejercicio en vivo: pedirle al grupo que escriba el URL actual del navegador y nombrar sus partes.

El viaje completo

Paso a paso: tu Enter → la página pintada

  1. Escribes la URL de la página.
  2. El navegador consulta al DNS para obtener la IP del servidor.
  3. El navegador envía una petición HTTP GET "dame la página /".
  4. El servidor responde el HTML (más o menos tiempo según cómo esté hecho: lo vemos en las próximas slides).
  5. El HTML revela que también se necesitan CSS, fuentes e imágenes: se piden por separado.
  6. El navegador construye la página (árbol de elementos), le aplica estilos y pinta.
  7. Si hay JS, se descarga, se ejecuta y puede modificar lo pintado.
En una ciudad: vas a comer a "La Casa del Parche" (URL). Le preguntas al portero (DNS) dónde queda. Caminas (IP). Al llegar, pides el almuerzo ejecutivo: "el plato principal" (HTML). Él te avisa que el almuerzo trae sopa, bebida y postre incluidos (CSS, imágenes, fuentes). Hasta que llega todo, la mesa no se sirve completa.
Recorrer los 7 pasos con UNA sola frase-resumen que se puedan llevar: "El navegador traduce el nombre, pide el HTML, y el HTML va jalando todo lo demás hasta pintarse." Detalle técnico de nivel: los pasos 5-7 se llaman "renderizado" y hay etapas específicas (parsing, CSSOM, paint) que solo mencionamos de nombre. En S11 (Lighthouse/performance) vamos a ahí con números. Hacer en clase la demostración con DevTools abierto: pestaña Network, recargar, y señalar en vivo cómo se ven las peticiones: el documento HTML primero, luego CSS/fuentes/imágenes, y el barrido del waterfall. Pedir que identifiquen qué recurso es de qué tipo. Este es el momento "¡ajá!" del día.

Percepción de velocidad

No todo tarda igual: el agua se va llenando

  • Primero llega el HTML → el navegador ya puede dibujar algo blanco o básico.
  • Luego CSS → apariencia aplicada.
  • Luego imágenes y fuentes → el último salto de calidad.
  • El JS puede retrasar todo si bloquea el render.

Por eso importa cuánto pesa cada recurso y en qué orden se pide: es más frecuente ver "la página con los estilos saltando" que una pantalla en negro.

Concepto a dejar sembrado ("toda la web se trata de eso"): la velocidad PERCIBIDA depende del orden y del peso de los recursos, no solo del hardware. La imagen que deben llevarse: "el HTML llega, y la página se viste por partes". En clase: con Network abierto y el throttling o navegando con red lenta (o simplemente la pestaña en modo reload lento), mostrar cómo la página aparece primero sin estilos y "salta" cuando llega el CSS. Explicar de pasada el término técnico FOUC (flash of unstyled content) por si alguien lo ve en redes, sin entrar en detalles. Marco mental: esto es la antesala de las métricas de rendimiento (LCP, FCP) de S11. No profundizar hoy, solo plantar la semilla.

La industria de hoy

Para entender la web actual, hay que ver cómo evolucionó

Años 90
Sitios estáticos simples
HTML en archivos
Actualizar = editar a mano
Años 2000
Páginas dinámicas (PHP, CMS)
HTML se arma al momento
Actualizar = tocar base de datos
Años 2010
SPA (React, Angular)
JS pinta todo en el navegador
Actualizar = muchas librerías
Hoy
Híbridos: SSG + SSR + CDN
Elegir según el caso
Actualizar = publicar y olvidar

Cada era resolvió algo: la primera fue manual, la segunda automatizó el contenido, la tercera hizo apps con interfaces complejas, y hoy volvemos a lo simple... pero a lo simple bien hecho.

Esta es la slide más importante del día a nivel conceptual. Recorrerla como una historia, no como un listado: 1. Años 90: HTML estático a mano. Actualizar una fecha = abrir el archivo, editar, volver a subir. Era un infierno para contenidos grandes → nace el problema "¿cómo hago una web con MUCHO contenido que cambie a menudo?". 2. Años 2000: PHP + CMS (WordPress, Joomla). La página ya no era un archivo: un PROGRAMA en el servidor generaba el HTML consultando una base de datos. Cada visitante recibía HTML cocinado al momento. Resolvió el contenido dinámico. Costo: cada visita = un pedido generado = más lento y más costo de servidor. 3. Años 2010: SPA (React/Angular). Ya no se mandaba HTML generado: se mandaba un HTML mínimo + un mega-archivo de JS, y el JS construía TODO en el navegador. Perfecto para aplicaciones tipo dashboards… pero pesadísimo para una landing: descarga todo, lo ejecuta, y recién ahí el visitante ve algo. Dejó un legado de sitios lentísimos. 4. Hoy: madurez. Nace la idea de "¿y si pre-cocino el HTML como en los 90 (rápido) pero con herramientas modernas?" = SSG. Y "¿y si lo cocino al momento solo cuando haga falta?" = SSR. Y "¿y si reparto los archivos por todo el mundo cerca del usuario?" = CDN. Los frameworks modernos (Astro, Next.js, SvelteKit) permiten mezclar. Moraleja a subrayar: la web de hoy no es "la más nueva tecnología", es "la que elige la herramienta correcta para el caso". Eso conecta directo con la filosofía del curso (criterio primero, no moda).

Las dos cocinas de hoy

SSG vs SSR: las siglas que importan

SSG
Static Site Generation		SSR
Server-Side Rendering
Cómo se cocinaEl HTML se arma antes, al publicarEl HTML se arma al momento, en cada visita
Rapidez para el visitanteInstantánea: solo se entrega archivosDepende del servidor y la DB
Costo del servidorMínimo: una vez por publicaciónPermanente
Riesgo / superficie de ataqueBajoAlto (código vivo, DB, sesiones)
Cuándo usarContenido que cambia poco: marketing, docs, blogsContenido vivo por usuario: apps, paneles, carrito
Comida: SSG = buffet preparado antes; SSR = cocina a la carta, cada plato a pedido.
Expandir las SIGLAS con calma: - SSG = Static Site Generation: "generación de sitio estático". La palabra mágica: generar. El HTML no se escribe a mano (como los 90): lo genera una herramienta (en nuestro caso Astro) en el momento de publicar. Resultado: archivos listos. - SSR = Server-Side Rendering: "renderizado en el lado del servidor". El servidor corre un programa que produce el HTML por cada petición. - Comparación en la analogía del restaurante: SSG es un buffet preparado a las 6:00, cuando llegas a las 13:00 te sirven al instante, y si la receta cambia, se recocina toda la bandeja en el próximo "deploy". SSR es cocinar tu plato al momento: más fresco y personalizable, pero tardas más y necesitas al cocinero (servidor) activo siempre. - Terminología que aparecerá salvaje en internet y conviene nombrar: ISR (Incremental Static Regeneration — refrescar páginas estáticas de a poco, de Next.js) y "edge". Basta con nombralas: si suena, ya se sabe qué preguntar en S7.

La decisión correcta

No es «estático bueno / dinámico malo»: es el caso de uso

Levanta la mano para ESTÁTICO (SSG)

  • El contenido cambia poco (noticias, agenda, docs)
  • Lo visitan muchos sin loguearse
  • Importa que cargue al instante
  • No hay datos personales que proteger

Levanta la mano para DINÁMICO (SSR)

  • El contenido es distinto para cada usuario
  • Hay sesiones, carrito, chat, login
  • Se consulta una base de datos en cada visita
  • Requiere personalización en tiempo real

Ejercicio con el grupo: decir sitios conocidos y pedir que los clasifiquen. (Correo electrónico → SSR. Página de un restaurante estático — SSG. Instagram — SSR/SPA.)

Ritmo de clase: leer las dos columnas y preguntar "¿glud.org, estático o dinámico? ¿Y Otro sitio que conozcan?" Dejar que discutan antes de revelar. Botón de datos duros: hoy muchas páginas de "marketing" de empresas son SSG justamente porque pesan menos, cargan más rápido y rankean mejor en buscadores. Y los frameworks modernos permiten "SSG por página": una web puede tener el 90% estático y 10% dinámico. Eso se llama arquitectura híbrida (Astro lo permite; lo vemos en S7). Mensaje a insistir: "estático vs dinámico" NO es una disputa de tecnologías, es una decisión de PRODUCTO: primero el usuario y el contenido, después la herramienta. Esta es la primera vez en el curso que practican "criterio antes que tecnología" y va a volver en TODAS las sesiones.

La industria de hoy: Netlify o Vercel toman los archivos estáticos generados, los reparten por servidores de todo el mundo (CDN) y el visitante descarga desde el más cercano. "Estático" no significa "simple": significa "pre-cocido y servido por una red mundial".
Conectar las 4 preguntas de la tabla con la decisión técnica. El punto pedagógico: escribir el razonamiento ANTES de la tecnología. La tabla es literalmente el proceso mental de quien diseñó el sitio. CDN = Content Delivery Network: red de servidores distribuidos que guardan copias de los archivos. El visitante de Bogotá descarga el archivo de un server en Bogotá, no en Estados Unidos. Resultado: web rápida en todo el planeta, sin tener un solo servidor propio. Dato de contexto para cuando pregunten "¿y Netlify qué paga?" — los planes gratuitos existen porque la CDN de archivos estáticos cuesta poco (son solo archivos); cuesta caro servirlos como dinámicos. Otra vez: la elección estática tiene consecuencias económicas reales.

Desde el código

El repositorio como fuente de verdad

Todo lo que ves en el sitio vive en GitLab, como texto con historia:

main        rama de producción  → lo que ve el mundo en glud.org
dev         rama de integración → los cambios aprobados se prueban juntos
feat/*      rama personal      → cada quien trabaja su cambio aquí

El flujo, tal y como lo usaremos todo el curso:

  1. Trabajas en tu rama feat/.
  2. Propones su inclusión con un Merge Request hacia dev.
  3. Otra persona revisa el código y aprueba.
  4. dev se integra a main cuando el conjunto está estable.
  5. Al llegar a main, Netlify re-cocina el sitio y lo publica: deploy automático.
Concepto sorpresa a explicar: el sitio se arma en un computador ajeno (el pipeline de CI), no en tu PC. Cuando el pipeline termina, la web se actualiza sola. Por eso nadie con una web en producción hace "subir archivos a mano" (era de los 90). Aquí el grupo ya usa GitHub o GitLab; si no, el README de git_course del grupo tiene el material del curso Git 101 para nivelar (enlace en el índice del curso). No profundizar en comandos git — HAY sesión dedicada (más adelante se decide si afuera en curso complementario o dentro del curso; en este programa básico, se enseña lo mínimo para no bloquearse y el flujo completo se practica en S13). Lo que hay que transmitir: el flujo mental de "rama personal → revisión → una sola rama estable". De paso sembrar la cultura GLUD: nunca se commit directo a main. Es la práctica de producción real del grupo.
