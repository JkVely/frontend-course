¿Por qué Astro y no React o Next?

Esta sesión no es "Astro es mejor que React". Es entender que cada herramienta tiene un caso de uso, y por qué para el sitio del GLUD la elección correcta fue Astro. Criterio antes que moda.

PREGUNTA GUÍA: "¿Han oído hablar de React, Next.js, Vue? ¿Saben para qué se usa cada uno?" Anotar. Luego: "¿Por qué creen que un sitio como glud.org —que no es una aplicación, es una página informativa— necesita React?" Nivel de entrada: habrán oído nombres. Nivel de salida: saben qué hace cada herramienta y por qué Astro encaja en un sitio estático de contenido.

Objetivos de la sesión

Al terminar vas a poder:

  1. Explicar qué hace React, qué hace Next.js y en qué se diferencian de Astro.
  2. Entender "islas de interactividad" y por qué enviarlo todo como JS es un problema en sitios de contenido.
  3. Justificar por qué glud.org usa Astro + SSG para su caso de uso.
  4. Leer la estructura básica de un proyecto Astro (pages, layouts, components).
Recorrer objetivos. Resaltar que hoy no van a escribir componentes React: van a entender el mapa de herramientas para no repetir el error de "usar React porque todo el mundo lo usa".

Construcción: React es como comprar una casa prefabricada completa con cableado y tuberías visibles; Next.js es esa misma casa pero con posibilidad de personalizar la entrega; Astro es construir la casa con materiales precocinados y solo instalar electricidad en las habitaciones que la necesitan.
Leer columna por columna. El punto central: React no es un "framework web" completo, es una librería de componentes. Next.js le añade servidor y rutas. Astro es distinto: asume que la mayoría de una web es contenido estático y solo activa JavaScript donde tú lo pides explícitamente.

El problema del "todo JS"

El navegador tiene que descargar y ejecutar todo

  • En un sitio hecho 100% con React, el visitante descarga un paquete de JavaScript grande antes de ver algo útil.
  • Eso se llama hidratación: el navegador toma el HTML y "reanuda" la interactividad con JS.
  • En un teléfono medio y una red regular de la universidad, eso se nota: la página se ve, pero los botones no responden hasta que termina el JS.
  • Para una landing informativa como glud.org, esa carga es innecesaria.
    • La industria de hoy: muchas empresas empezaron con React para todo y ahora migran partes a Astro o Next.js por rendimiento. No es que React sea "malo": es que usarlo para una página de información es como usar un camión de mudanza para llevar una carta.
    Explicar hidratación con palabras simples: el servidor envía el HTML pintado, pero para que sea "vivo" (botones que reaccionan), el navegador debe descargar el JS y "conectarlo" al HTML. Ese proceso cuesta tiempo y batería. En S10 (animaciones) verán cómo Astro maneja esto con islands.

La solución de Astro

Islas de interactividad

Astro genera HTML estático puro por defecto. El JavaScript solo existe en "islas" que tú marcas explícitamente:

<Button client:visible />    <-- se activa cuando entra en la pantalla
<Menu client:idle />           <-- se activa cuando el navegador queda libre
<Counter client:load />        <-- se activa al cargar la página
<Card />                         <-- solo HTML, cero JS

Una isla sin client:* no envía JavaScript al visitante. Cero.

Casa: la mayoría de las habitaciones son solo paredes y muebles (HTML). Solo la cocina y el baño tienen tuberías y cables (JavaScript). No cableas toda la casa para usar el fregadero de la cocina.
Mostrar el código y explicar cada directiva client:*. El mensaje: tú decides qué es interactivo. Todo lo demás es HTML veloz. Conectar con S0: esto es por qué glud.org carga ~8 KB de JS propio, no megabytes.

Cierre

La regla del curso

No usamos una herramienta porque es popular. La usamos porque resuelve el problema del usuario con el menor costo.

Una frase para llevarse: React y Next son para aplicaciones; Astro es para sitios de contenido. glud.org es un sitio de contenido.
