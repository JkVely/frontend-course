pnpm: por qué no usamos npm

El curso eligió pnpm deliberadamente. Esta sesión no es "comando contra comando": es entender el ecosistema de dependencias para que, al ver un package.json o un pnpm-lock.yaml, sepas exactamente qué hay escrito ahí y por qué.

PREGUNTA GUÍA: "¿Qué pasó la última vez que clonaste un proyecto y no funcionó al instalar dependencias?" Anotar respuestas: versiones distintas, fallos de red, node_modules gigante. Esa es la motivación de la sesión. Nivel de entrada: saben que existen las librerías. Nivel de salida: entienden el lockfile, el store de pnpm, por qué el curso prohíbe npm en este equipo, y los scripts del package.json.

Objetivos de la sesión

Al terminar vas a poder:

  1. Explicar qué es un gestor de paquetes y para qué sirve.
  2. Diferenciar package.json, package-lock.json (o pnpm-lock.yaml) y node_modules/.
  3. Explicar por qué el curso usa pnpm vía corepack y prohíbe npm.
  4. Leer scripts de package.json y ejecutarlos con corepack pnpm run.
  5. Instalar, eliminar y actualizar una dependencia con pnpm.
Recorrer cada objetivo rápidamente. El punto clave de este bloque: no se trata de saber todos los comandos, de entender qué archivos son fuente de verdad y cuáles son artefactos generados.

El ecosistema de dependencias

Tres archivos, tres papeles

ArchivoQué es¿Se edita a mano?¿Se sube a Git?
package.jsonManifiesto: nombre, versión, scripts y dependencias que tú eligesSíSí
pnpm-lock.yamlLockfile: versiones exactas resueltas de cada paquete y sus dependenciasNoSí (fuente de verdad)
node_modules/Código descargado de todos los paquetesNoNo (se ignora con .gitignore)
Análisis: package.json es la lista de compras que escribiste. pnpm-lock.yaml es el ticket de compra con precios y cantidades exactas del día que compraste. node_modules es la despensa: la vas a usar, pero no la llevas de mudanza porque se vuelve a llenar con el ticket.
Enfatizar: el lockfile es fuente de verdad, no package.json. Si dos personas instalan desde el mismo lockfile, obtienen idéntico código. Sin lockfile, cada quien puede terminar con versiones distintas y bugs que "en mi PC sí funciona". Regla del curso: nunca borrar el lockfile a menos que sepa exactamente por qué.

¿Por qué pnpm y no npm?

pnpm (este curso)

  • Guarda cada versión de cada paquete una sola vez en un store central
  • node_modules son enlaces simbólicos (hard links): más ligero y rápido
  • Instalaciones deterministas y más seguras
  • Compatible con el ecosistema de Node/Astro

npm (prohibido aquí)

  • Copia paquetes en cada proyecto: node_modules más pesado
  • En este equipo, npm ha corrompido lockfiles ("Lock compromised")
  • Menos determinista en instalaciones repetidas
La industria de hoy: pnpm es el estándar creciente en proyectos modernos (Vite, Astro, Turborepo lo usan). No es una preferencia personal del profesor: es una decisión técnica con consecuencias en velocidad de instalación, peso en disco y reproducibilidad.
Contar la historia real del equipo: una vez npm rompió el lockfile de un proyecto del grupo y se perdió tiempo reconstruyéndolo. Por eso la regla dura: "pnpm vía corepack, NUNCA npm". Explicar corepack: es el gestor que trae Node para activar pnpm sin instalarlo aparte. No se instala pnpm con npm.

Cómo funciona pnpm por dentro

El store y los enlaces

  • Cuando instalas un paquete, pnpm lo descarga una vez al store local (~~/.local/share/pnpm/store en Linux).
  • En el proyecto, node_modules/ contiene enlaces a ese store, no copias.
  • Si dos proyectos usan React 18.2, React se descarga una sola vez en tu computador.
  • Estructura de node_modules más limpia: no anida dependencias innecesarias (salvo que el paquete lo exija).
Biblioteca: npm compra un libro para cada alumno (costo de espacio alto). pnpm compra un libro y lo pone en la biblioteca central; cada alumno recibe una tarjeta que apunta a ese libro (enlace simbólico). Mismo contenido, mucho menos espacio usado.
Mostrar en vivo (si hay conexión y tiempo): corepack pnpm store path para ver dónde vive el store, y ls -la node_modules para notar que muchos elementos son enlaces, no carpetas normales. Esto demuestra por qué pnpm instala más rápido y pesa menos en disco.

Scripts del proyecto

Leer y ejecutar scripts

{
  "name": "glud-website",
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "format": "prettier --write ."
  },
  "devDependencies": {
    "astro": "^5.0.0",
    "prettier": "^3.0.0"
  }
}

Los scripts son atajos. En lugar de escribir el comando completo, ejecutas:

corepack pnpm run dev
corepack pnpm run build

Y si es un script de pnpm propio, puedes omitir run: corepack pnpm dev.

Explicar que los scripts centralizan comandos para que todo el equipo use los mismos parámetros. Mostrar que astro dev levanta el servidor de desarrollo y astro build genera los archivos estáticos. Conectar con S0: este es el mismo comando que usaron para levantar el sitio en la sesión 0.

Instalar, eliminar, actualizar

Los comandos que van a usar todo el semestre

AcciónComando con pnpmQué hace
Instalar dependencias del proyectocorepack pnpm installLee el lockfile y llena node_modules
Agregar una libreríacorepack pnpm add nombre-paqueteInstala y actualiza package.json + lockfile
Agregar como herramienta de desarrollocorepack pnpm add -D nombre-paqueteLo guarda bajo devDependencies
Eliminar una libreríacorepack pnpm remove nombre-paqueteLa borra de package.json, lockfile y node_modules
Actualizar todocorepack pnpm updateRespeta rangos de versión y reescribe el lockfile
Regla de oro del curso: nunca editar pnpm-lock.yaml a mano. Siempre se modifica mediante estos comandos. Si alguien agregó una dependencia a package.json "a ojo", debe correr pnpm install para que el lockfile se reconcilie. En clase, mostrar un ejemplo real: instalar uuid y ver cómo cambian package.json y el lockfile.

Ejercicio guiado

EN CLASE (10 min):
  1. Clonen el sitio del GLUD si aún no lo tienen: git clone ...
  2. Instalen con corepack pnpm install.
  3. Levanten con corepack pnpm dev y confirmen localhost:4321.
  4. Instalen un paquete de prueba: corepack pnpm add chalk.
  5. Observen qué cambió en package.json y en pnpm-lock.yaml.
  6. Eliminenlo: corepack pnpm remove chalk.
Apoyar a quien se atasque en la instalación (node, corepack, permisos). El objetivo no es que dominen chalk, sino que vean el ciclo completo: instalar → observar cambios → eliminar. Si alguien ya tiene todo instalado, que ayude a su compañero (niveles de reto como mentores de mesa, como dice el README del curso).

Lo que NO hacen con pnpm

Reglas duras del curso

  • No instalar nada con npm install.
    • Si ven un tutorial que dice npm install ..., traduzcanlo mentalmente a corepack pnpm add ....
  • No hacer npm init para crear proyectos nuevos.
    • El curso usa el repositorio del GLUD como base; no se crean proyectos desde cero en este bloque.
  • No subir node_modules/ a Git.
    • Está en .gitignore. Si suben esa carpeta, el MR no se acepta.
  • No borrar pnpm-lock.yaml "porque pesa".
    • Es el archivo que garantiza que todos tengan lo mismo.
Recordar: estas reglas no son capricho. Vienen de la experiencia del grupo con npm rompiendo lockfiles. Quien respete estas reglas no tendrá el problema de "en mi PC funciona y en la de mi compañero no".
