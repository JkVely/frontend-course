De dónde sale la agenda y los cursos

Todo el contenido que ves en glud.org (agenda de la SLUD, horario de cursos, proyectos, ponentes) no está escrito a mano en cada página HTML. Vive en archivos de datos tipados con TypeScript que Astro lee al generar el sitio.

PREGUNTA GUÍA: "Si quieren cambiar la fecha de un evento, ¿tienen que editar el HTML de la página? ¿O hay un archivo separado con las fechas?" Nivel de entrada: han visto las páginas con contenido. Nivel de salida: saben que el contenido vive en src/data/*.ts, entienden por qué TypeScript lo protege, y saben cómo se inyecta en las páginas.

Objetivos de la sesión

Al terminar vas a poder:

  1. Explicar la diferencia entre contenido duro (en el HTML) y contenido dinámico de un SSG (en archivos de datos).
  2. Leer un archivo de datos del sitio (activities.ts, coursesData.ts) e identificar su forma.
  3. Explicar por qué esos archivos usan TypeScript y qué protegen.
  4. Rastrear cómo un dato de esos archivos llega a una tarjeta renderizada en la página.
Resaltar: esta sesión es el puente entre "diseño" (S2-S3) y "datos reales". El contenido ya no es lorem ipsum; es información que alguien va a tener que mantener.

Contenido duro vs contenido de datos

Contenido duro (estático)

  • Escrito directamente en el .astro
  • Para cambiarlo, se edita la página y se vuelve a publicar
  • Ejemplo: el título de la home, el lema del footer

Contenido de datos (SSG)

  • Vive en src/data/*.ts (no en el HTML)
  • Para cambiarlo, se edita el archivo de datos y se vuelve a generar
  • Ejemplo: cada curso con nombre, fecha, instructor, cupo
Menú de restaurante: el contenido duro es el marco del menú (el marco de madera nunca cambia). El contenido de datos son los platos del día: se escriben en una pizarra aparte y el mesero los lee para cada comensal. Cambiar la pizarra no implica reconstruir el marco.
Explicar que en un SSG el "contenido dinámico" no es que el servidor consulte una base de datos en cada visita: es que, al momento de generar el sitio (build), Astro lee los archivos de datos y los incrusta en el HTML. Resultado: la velocidad del estático con la mantenibilidad del contenido separado.

Por qué TypeScript para los datos

Los contratos de S5 aplicados al contenido

interface Actividad {
  titulo: string
  ponente: string
  hora: string
  dia: string
  tipo: "charlas" | "talleres" | "instalaciones"
}

Si alguien escribe tipo: "conferencia" (no previsto), TypeScript lo marca antes de generar el sitio. Si olvida hora, también.

En JavaScript puro ese error llegaría al visitante: una tarjeta vacía o un "undefined" en la pantalla.

Conectar con S5: interfaces, union types, strict null checks. Aquí se ve el valor real de TS: no es teoría, es evitar que la agenda de la SLUD se muestre rota porque alguien escribió mal un campo. Mostrar un ejemplo real de error que TS atrape en activities.ts si es posible.

De los datos a la página

El flujo: dato → componente → HTML

  1. astro build lee src/data/activities.ts.
    2. Astro importa los datos y los pasa como propiedades a los componentes de Astro.
  2. Cada actividad se renderiza como una tarjeta (ActivityCard). El componente recibe titulo, ponente, etc., y los pinta en HTML.
  3. El resultado final es HTML estático con los datos ya dentro. El visitante recibe la página lista, sin que el servidor consulte nada en tiempo de ejecución.
<ActivityCard
  titulo={actividad.titulo}
  ponente={actividad.ponente}
  hora={actividad.hora}
/>
Recorrer los 4 pasos lentamente. Es el núcleo mental de un SSG: datos en archivos, componentes que los consumen, HTML generado una sola vez. Conectar con S7 (Astro genera HTML) y con S0 (el sitio es estático).

Cursos: el caso de LimeSurvey

No todo vive en el repo

Los cursos GNUBIES se muestran en /cursos, pero la inscripción no ocurre en el sitio. Vive en LimeSurvey (lime.glud.org), una plataforma externa.

  • La tarjeta de cada curso muestra: nombre, instructor, imagen y un botón "Inscribirse".
    • Ese botón es un enlace externo a LimeSurvey con el curso preseleccionado.
  • LimeSurvey tiene X-Frame-Options: SAMEORIGIN, por tanto nunca se embebe en un iframe. Siempre se abre en pestaña nueva con target="_blank" rel="noopener noreferrer".
La industria de hoy: los sitios modernos no lo hacen todo ellos. Usan servicios especializados para inscripciones, pagos, formularios o encuestas, y se integran con enlaces. La pregunta clave no es "¿lo construimos nosotros?", es "¿quién lo hace mejor y cómo lo conectamos de forma segura?".
Mostrar en vivo la página /cursos, hacer clic en "Inscribirse" y observar que se abre una pestaña externa. Explicar por qué no se puede meter LimeSurvey en un iframe (cabecera de seguridad del servidor de LimeSurvey) y por qué rel="noopener noreferrer" es obligatorio al abrir enlaces externos en pestaña nueva (seguridad contra tabnabbing).

Ejercicio guiado

EN CLASE (10 min):
  1. Abrir src/data/activities.ts y leer una actividad completa.
  2. Buscar esa misma actividad en la página /actividades del sitio levantado localmente.
  3. Proponer un cambio de texto (ej: corregir una hora) en el archivo .ts.
  4. Ejecutar corepack pnpm build y verificar que el cambio aparece en el HTML generado.
Este es el momento "entiendo de dónde sale el contenido". Apoyar a quien tenga problemas con el build. El resultado clave: ven que editar un archivo de datos y reconstruir actualiza el sitio, sin tocar HTML a mano.

Cierre

El contenido es datos, no maqueta

En este sitio, cambiar una fecha de evento significa editar un archivo de datos, no abrir el HTML de la página. Eso separa quién escribe contenido de quién maqueta, y TypeScript evita que un dato mal escrito rompa la vista.

Una frase para llevarse: el contenido vive en archivos tipados; las páginas solo lo muestran. Eso es lo que permite un SSG rápido y mantenible.
